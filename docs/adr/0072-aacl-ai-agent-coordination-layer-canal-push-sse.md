# ADR-0072 — AACL — AI Agent Coordination Layer: canal push (SSE/WS), leases por archivo, detect_conflicts y DAG de dependencias

- **Status:** proposed
- **Date:** 2026-07-12
- **Components:** src/coord, src/server, src/mcpserver, web

## Context

Con ADR-0054 + ADR-0071 el harness ya es un bus de coordinación pull completo (claim/release/publish/poll/status) consumible por cualquier host MCP. El usuario pregunta por suscripción push («¿via websocket?») para que N agentes en N harneses (Claude Code, Codex, Gemini CLI, OpenCode) sobre el mismo proyecto se enteren al instante de cambios (types/ cambió → todos deberían saberlo). Realidad técnica que condiciona el diseño: (1) MCP es request-response; no define webhooks ni pub/sub; el transporte moderno (Streamable HTTP) permite notificaciones server→cliente y suscripciones a resources, pero el soporte en los hosts es inconsistente; (2) aunque hubiera push de transporte, un agente LLM SOLO escucha en fronteras de turno — un push no despierta al modelo a mitad de idle; quien puede reaccionar en tiempo real es el WRAPPER/harness, no el LLM; por eso el patrón correcto para el modelo es pull en frontera de turno (el hook Stop ya corre coord poll, y coord_status al abrir sesión quedó en el contrato de AGENTS.md). (3) La coordinación actual es por task_key libre; no hay noción de recursos (archivos/globs) ni conflictos ni dependencias.

## Decision

Evolucionar la coordinación a una capa AACL en cuatro rebanadas, manteniendo MCP como fachada única para los agentes y el push como canal para HARNESSES/wrappers: (R1) Canal push de solo-difusión: endpoint SSE `GET /api/coord/stream?project=` (y opcional WebSocket) en el server web existente (auth de ADR-0046), alimentado por Mongo change streams sobre coord_events (atlas-local es replica set de un nodo: soportado) con fallback a tail-polling interno; los wrappers lo consumen y encolan para el turno siguiente del agente; el LLM sigue en pull. (R2) Leases por recurso: claim_task gana `resources: string[]` (globs, p.ej. src/auth/**) además del task_key; índice por (project, resource); `acquire`/`release` heredan el TTL de ADR-0054. (R3) `detect_conflicts` {project, files[]}: cruza los archivos que un agente VA a tocar contra los leases activos y los file_changed recientes → {locked_by, overlaps, advice}; publish_event gana type `file_changed` (payload files[]) emitido por capture-session/run-host al cierre. (R4) DAG de dependencias: task_claims gana `depends_on: task_key[]`; al release(done) se emite task_done y los claims bloqueados pasan a ready (evento `task_ready`) — quien haga poll/status lo ve sin busy-waiting. Métricas de tesis derivadas: conflictos evitados, tiempo de espera por lease, retrabajos, agentes concurrentes por ventana. El broker interno (Redis Streams/NATS) queda explícitamente FUERA del v1: Mongo change streams bastan al volumen actual y no añaden dependencia operativa; la interfaz MCP no cambiaría si después se enchufa un broker.

## Consequences

Los agentes siguen hablando MCP puro (portabilidad total entre hosts); los harneses ganan reactividad real sin violar el modelo de turnos del LLM; la coordinación pasa de «locks por nombre de tarea» a «leases por recurso + conflictos + dependencias», que es la contribución diferenciable para la tesis (capa de coordinación agnóstica multi-harness, más que un gestor de memoria). Costos: el canal SSE añade superficie al server web (auth/lifecycle), los change streams exigen replica set (cumplido en atlas-local y Atlas cloud; el fallback interno cubre standalone), y los globs de leases requieren una semántica de solapamiento conservadora (glob∩glob) que debe sobre-avisar. Cada rebanada aterriza con tests y su ADR accepted referenciando este.
